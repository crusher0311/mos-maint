# MOS Maintenance MVP

## Overview
MOS Maintenance MVP is an AI-enhanced automotive maintenance management system designed to optimize operations for auto shops. It provides tools for managing vehicle maintenance recommendations, customer data, and multi-shop user management. The system aims to boost operational efficiency and customer engagement through an intuitive dashboard, various integrations, and AI-powered insights, positioning itself as a leading platform for automotive service management.

## System Architecture
The application is built with Next.js 14.2.5, React 18, Next.js API Routes, and Tailwind CSS, primarily using TypeScript. It employs a dual-database strategy with Supabase PostgreSQL for core relational data and MongoDB Atlas for caching and legacy features.

**Build/Deploy — `openapi-types` must stay a direct dependency (do not remove):** The recurring Render build failure (`Missing: openapi-types@12.1.3 from lock file`) had a single true root cause: `openapi-types` was only a *transitive peerDependency* of `@apidevtools/swagger-parser` (pulled in via `swagger-jsdoc → swagger-parser`), and the committed `package-lock.json` carried only the peer *declaration* (`"openapi-types": ">=7"`) with **no resolved `node_modules/openapi-types` package entry**. Render's build runs `npm install` (lenient — `buildCommand: npm install; npm run build; ./render-build.sh`), which fetched the missing peer on the fly and *passed install*, but the build then runs `prebuild → test:smoke`, whose first step is the strict lockfile guard `scripts/check-lockfile-sync.cjs` (`npm ci --dry-run`). Strict `npm ci` everywhere (local and Render) rejected the lockfile for the missing entry → build died in prebuild, NOT at install. Fix: `openapi-types` is now pinned as a direct `dependency` (`^12.1.3`) in `package.json`, so every npm version writes a deterministic top-level `node_modules/openapi-types` entry into the lockfile and `npm ci` is satisfied. The earlier Node-version theory was a red herring — the issue was never npm-version drift, it was a peer dep that was never anchored. Node is still pinned to `20.20.0` via `.node-version`/`.nvmrc`/`engines` for reproducibility (harmless to keep). The drift guard stays wired to the front of `test:smoke`/`prebuild`. **Do not move `openapi-types` back to a transitive-only peer, and do not delete the guard.** When you change `package.json` deps, always run `npm install --package-lock-only` and commit `package-lock.json`.

*   **Authentication & Authorization**: Role-based access is implemented with bcrypt hashing and token-based authentication. Task #502 — every 401/503 from `/api/extension/*` carries a stable `code` field in the JSON body (`TOKEN_MISSING | TOKEN_INVALID | TOKEN_EXPIRED | SHOP_FORBIDDEN | AUTH_LOOKUP_FAILED`) so the Chrome extension can distinguish terminal credential failures from transient server hiccups. `lib/extension-auth.ts` exports `buildAuthErrorBody(auth, extra?)` — all extension routes return their auth-error body through it so the code is never accidentally dropped. The extension (`mos-tools-extension/background.js` `handleMosApiRequest`) now retries 401s with exponential backoff + jitter (`MOS_AUTH_RETRY_DELAYS_MS = [500, 1500, 4000]`) before a single silent re-auth, and only clears `mosApiToken` from `chrome.storage.local` when (a) the retry budget is exhausted AND (b) silent re-auth also fails AND (c) the latest 401's `code` is exactly `TOKEN_INVALID` (the only code that means "your credentials are dead — log out now"). Every other code (`TOKEN_EXPIRED`, `TOKEN_MISSING`, `SHOP_FORBIDDEN`, `AUTH_LOOKUP_FAILED`, unknown) is soft: the extension throws `MOS_SESSION_SOFT_EXPIRED` with the token left in place so the user is not bounced to login mid-shift. As an additional safety net during the W4 PG-identity cutover, `validateExtensionToken` falls back to a Mongo `users.extensionToken` read on PG-miss when `IDENTITY_PG_CANONICAL=1` is set, logging `[Extension Auth] pg_miss_mongo_hit user=<masked>` so drift can be quantified. Locked in by `tests/extension-auth-401-codes.smoke.ts` and `tests/extension-401-retry-policy.smoke.ts` — do not regress to the destroy-on-first-401 behavior.

*   **Tekmetric Shared Rate Limiter**: Cross-process per-second rate limiter at `lib/integrations/tekmetric/shared-rate-limiter.ts` ensures the combined attempted RPS across all Node processes/services sharing the same Tekmetric OAuth credentials never exceeds Tekmetric's per-key cap. Uses a Mongo-backed token bucket keyed by unix second (collection: `tekmetric_rate_buckets`, TTL ~10s). Tune the global cap with `TEKMETRIC_SHARED_RPS_CAP` (default 8, hard ceiling 10). Break-glass: `TEKMETRIC_SHARED_LIMITER_DISABLED=true` short-circuits the limiter entirely; `TEKMETRIC_SHARED_LIMITER_FAIL_OPEN=true` flips the over-cap timeout from fail-closed (default — caller backs off and retries) to fail-open (caller pass-through with a "CAP BREACH" warning log). Inspect live state with `db.tekmetric_rate_buckets.find().sort({_id: -1}).limit(10)`. On Mongo failure the limiter falls back to per-process behavior with a warning log.
*   **Tekmetric Full-Page Per-Shop In-Flight Lock**: `lib/integrations/tekmetric/inflight-lock.ts` adds per-shop concurrency control to the full-page backfill route. Both the GET cron and POST `{shopId}` handlers acquire a Mongo-backed lock on the existing `tekmetric_backfill_progress` doc (fields `inFlightUntil`, `inFlightStartedAt`, `inFlightOwner`). Default TTL is 6 minutes — a crashed process self-heals on the next cron tick after expiry. POST returns HTTP 409 with `heldBy`, `heldUntil`, and `startedAt` if a run for that shop is already in flight; the GET cron logs and skips the shop instead of starting a duplicate. Lock state is observable on the `catchup-status` endpoint (`inFlightUntil` / `inFlightStartedAt` / `inFlightOwner` on each shop row). Release is owner-scoped so a runaway promise's `finally` cannot clear a TTL-recovered lock.

*   **PG Canonical FK Invariant (Skip-Path Backfill)**: `lib/integrations/core/normalized-ingestion.ts` `ingestWorkOrder` and `ingestServiceJob` historically short-circuited on a contentHash match without writing to PG, which left Mongo docs from before the W3a polarity flip (task #344) with no PG counterpart and produced FK 23503 violations on child `service_jobs` / `line_items`.
